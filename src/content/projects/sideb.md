# My Role

Flutter Web 클라이언트를 전담했습니다. 검색부터 로딩, 결과 그래프·그룹 목록까지 사용자가 거치는 화면을 만들었고, `POST /recommend` 응답을 화면에 연결하는 API 클라이언트와 모델을 맡았습니다. Last.fm·iTunes·Deezer 연동과 추천 알고리즘 자체는 백엔드 담당입니다.

### 1. 화면 흐름

검색 화면과 결과 화면을 목업으로 먼저 띄운 뒤, `search_screen` / `result_screen`으로 나눴습니다. 검색에서는 Enter로 요청을 보내고, 최근 검색어 태그·상단 키워드 표시·화면 전환 애니메이션을 붙였습니다. 결과 화면에서는 유사·반대·숨은 곡 그룹을 그래프와 앨범 이미지로 보여 주고, 그룹을 누르면 갤러리 또는 리스트로 곡 목록을 보게 했습니다.

### 2. API 연동

`RecommendationApi`와 응답 모델로 검색어(`query`)와 개수(`top_n`)를 보내고, 기준 트랙과 카테고리별 추천 목록을 결과 화면에 연결했습니다. 백엔드 요청 형식이 `query`로 바뀌는 과정에서 바디를 맞췄고, Docker·브라우저에서 `localhost`가 IPv6로 잡히면 호출이 실패해 `127.0.0.1`로 보내도록 클라이언트에 넣었습니다.

### 3. 대기·실패 처리

추천이 끝날 때까지 로딩 창을 유지하고, 안내 문구가 줄바꿈으로 깨지지 않게 맞췄습니다. 곡을 찾지 못하면 안내를 띄우고, 최근 검색어는 성공한 결과만 남기도록 했습니다.

### 4. 결과 화면의 기준 트랙

추천 1위가 아니라, 사용자가 검색한 곡이 메인 카드에 고정되게 했습니다. 결과가 뜨는 순서, 그래프 분위기, 그룹 상세의 헤더와 뒤로 가기까지 시연 흐름에 맞춰 다듬었습니다.

# Retrospective

### 1. 화면을 먼저 그려도, 요청 형식이 바뀌면 검색 흐름이 다시 흔들렸다

목업과 화면을 먼저 나눈 뒤 API를 붙였는데, 요청을 `query` / `top_n`으로 바꾸고 로딩을 응답이 올 때까지 유지하는 수정이 이어졌습니다. 하루짜리 해커톤에서도 화면을 빨리 만드는 일보다, 주고받는 형식을 먼저 맞춰야 검색→대기→결과가 안정됐습니다.

### 2. 결과 화면의 핵심은 추천 1위가 아니었다

메인 카드를 랭킹 순으로 두면, 검색한 곡이 아니라 알고리즘이 고른 곡이 가운데에 왔습니다. 사용자가 방금 검색한 곡을 기준으로 둔 뒤에야 유사·반대·숨은 곡이 곁가지로 읽혔습니다. 데이터가 많아도, 화면에 무엇을 가운데 둘지는 프론트가 정해야 했습니다.

### 3. 실패한 검색을 성공처럼 쌓으면 기록이 거짓이 된다

없는 곡에도 최근 검색어를 남기면 태그는 늘어나는데 결과는 비었습니다. 실패 안내를 따로 두고 성공한 검색만 저장하면서, 빈 응답을 정상 결과와 같은 길로 보내면 안 된다는 점을 확인했습니다.

### 4. 시연 직전 디테일이 검색 사용감을 가른다

입력창 커서 위치, Enter 검색, 로딩 문구 줄바꿈, 검색 애니메이션처럼 기능 추가가 아닌 다듬기가 후반에 몰렸습니다. 하루 만에 추천 결과를 보여 주는 것보다, 검색하고 기다리는 동안 어색하지 않게 만드는 일이 시연에서 더 크게 보였습니다.

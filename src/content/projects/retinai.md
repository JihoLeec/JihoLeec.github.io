당뇨병성 망막병증은 당뇨병의 주요 합병증 중 하나로, 진행될수록 시력에 심각한 영향을 줄 수 있습니다.
사용자가 안저 이미지를 업로드하면 시스템에서 이미지를 분석하고, 망막병증의 이상 여부를 분석 결과와 함께 AI가 판단한 근거를 시각적으로 확인할 수 있도록 구성한 프로젝트입니다.

단순히 결과값만 제공하는 것이 아니라, 분석 가능한 이미지인지 먼저 확인하고, 병변 위치를 시각적으로 표시한 뒤 분석 결과를 pdf 형태로 제공하는 흐름으로 사용자가 결과를 이해할 수 있도록 하는 데 초점을 맞췄습니다.

※ 본 프로젝트는 의료진의 진단을 대체하기 위한 목적이 아닌, 의료적 판단을 보조하기 위한 프로토타입으로 진행된 프로젝트입니다.

# My Role

Flutter 클라이언트를 전담했습니다. 이미지 업로드부터 분석 대기, 결과·이력·PDF까지 사용자가 실제로 거치는 화면을 설계·구현하고, 그 화면이 백엔드 분석 API와 맞물리도록 REST 클라이언트와 응답 파서를 맡았습니다. AI 모델과 FastAPI 서버 자체는 담당이 아닙니다.

### 1. 화면 흐름

<img src="/images/eye/eye-history.png" alt="history screen">

<br>`/upload` → `/result` → `/history` 세 화면을 중심으로 동선을 구성했습니다. 업로드 화면에서는 이미지 선택·미리보기와 10MB·확장자 검증을 하고, 결과 화면에서는 원본·XAI 히트맵·판정·PDF 공유를 한곳에서 고르게 했으며, 이력 화면에서는 목록·무한 스크롤·판정/기간 필터·삭제를 붙였습니다. 결과 화면은 종착점이 아니라 재업로드와 이력으로 이어지는 허브로 두었습니다.  
<br>

### 2. API 연동

`EyeApiClient`로 멀티파트 업로드(`POST /analyze` → 202 + job_id), job 폴링, 이력 조회/삭제, 서버 로그, 배포 성능 지표를 연결했습니다. 백엔드가 내려주는 응답 키와 오류 코드(`not_fundus_image`, `low_image_quality` 등)를 프론트 모델에 맞춰 파싱하고, 화면에는 코드가 아니라 사용자가 이해할 문구로 보이게 했습니다.  
<br>

### 3. 분석 대기 UX

<img src="/images/eye/eye-polling.png" alt="polling" style="width: 50%; height: auto;" />

<br>서버 `phase`는 단계마다 점프하므로, 화면 진행률은 따로 보간했습니다. 폴링 결과를 진행 다이얼로그의 퍼센트·단계 문구로 풀어, 추론이 길어져도 멈춘 것처럼 보이지 않게 했습니다. 서버 로그와 성능 지표 다이얼로그, Esc·Enter로 조작 가능한 알림도 같은 맥락에서 시연·데모 사용자가 기다리는 동안의 불안을 줄이려 넣었습니다.  
<br>

### 4. 시연 배포

졸업작품 시연을 위해 macOS에서 실행 가능한 애플리케이션을 빌드했습니다. 웹 시연용으로는 Flutter Web + nginx Docker 설정도 프론트 쪽에 두었습니다.  
<br>

# Retrospective

### 1. 프론트는 화면이 아니라 시스템 통합이었다

10주 동안 프론트엔드를 맡으면서, Flutter가 화면을 그리는 도구가 아니라 네트워크·API 계약·상태 관리·예외 표현까지 묶는 시스템 통합 레이어라는 점을 체감했습니다. 업로드, 타임아웃, 라우트 인자, 네트워크 이미지, job 폴링, 서버 로그, lesion XAI, deploy metric이 한 화면에 이어질수록 막히는 지점이 UI가 아니라 계약과 데이터 형태에 있었습니다. 스프린트가 거듭될수록 “왜 이렇게 되는지”를 먼저 묻고, 원인이 화면 밖 합의인지 코드 안인지를 나누는 습관이 생겼습니다.

### 2. 기능 추가보다 데이터 정합과 동선이 먼저였다

이력 기능을 붙일 때는 화면을 먼저 만드는 일보다, 백엔드 응답을 프론트 파서와 맞추는 일이 핵심이었습니다. 응답 키와 상태 의미가 중간에 바뀌면 구현 속도가 빨라도 후반에 수정이 겹쳤고, 기능 추가보다 데이터 정합성과 스펙 고정 시점이 일정을 좌우한다는 것을 배웠습니다. 결과 화면 역시 분석값을 보여주는 종착점이 아니었습니다. 줌 확인, 재업로드, 이력 이동, PDF 내보내기를 한곳에서 고르는 허브였고, 이후에는 컴포넌트보다 사용자 동선이 끊기지 않는지를 먼저 보게 되었습니다.

### 3. 실제 사용자라고 가정하고 UX를 다듬었다

직접 이 보조 도구를 쓴다고 가정하고 화면을 다시 보면서, 병변 위치 위에 그림을 그리는 기능과 이력 필터를 추가했습니다. 가독성이 떨어지는 요소를 고치고, 주요 버튼이 Esc·Enter로도 동작하게 해 시연과 실제 사용 모두에서 손이 덜 가게 했습니다. 후반에는 백엔드가 새로 준 계약을 화면에 빠르게 반영하는 것과 함께, 의사·데모 사용자가 기다리는 동안 느끼는 불안을 줄이려 스피너, 오류 메시지, 진행 표시를 다듬었습니다. 라벨 정리, 이미지 표시 안정화, 파싱 보정처럼 겉으로 작은 작업이 앱을 믿을 수 있게 만든다는 점도 이 과정에서 분명해졌습니다.

### 4. Git은 커밋이 아니라 리뷰 단위로 나눠야 했다

협업에서는 Git 사용 방식이 가장 크게 남았습니다. 이전에는 깃을 어느 정도 안다고 생각했지만, 커밋만 보면 프론트 개발과 레포 전체 정리가 한 줄에 섞여 있었습니다. 팀 규칙상 frontend 브랜치는 UI·클라이언트가 중심인데, 통합 속도를 위해 chore로 백엔드를 끌어온 적이 있었고, 리뷰어 입장에서는 부담이었을 수 있습니다. 이후에는 동기화는 명시적인 chore PR로 두고, 기능은 feat/refactor만 남기려 합니다. 규모가 있는 팀에서는 브랜치와 PR을 역할 단위로 나누는 규칙을 더 일찍 맞춰야 한다는 점을 배웠습니다.
